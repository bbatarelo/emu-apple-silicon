# Software-monitoring latency measurements — 2026-11-16

## Scope and state

E-MU 0404 USB and Tracker Pre, installed driver **0.1.1 (git 9b96335-dirty)**, Apple Silicon
macOS 26.7.1 (25G241), arm64. Test source checkout: `5921d33`, branch `codex/emu-control-app`.
The installed driver was not rebuilt or replaced. Source and installed driver
are different revisions; these results characterize the installed binary.
Both units were measured separately, with cables moved between them.
176.4/192 kHz were not tested.

Both devices were restored to their original 48 kHz / 512-frame IO buffers after testing.
Volume and safety settings were not changed. Reported safety offsets were 5 ms
input and 4 ms output. Hardware direct monitoring was requested off and the user
confirmed the wiring ready. Input gain settings were not recorded. Output volume
was 1.000 on 0404 and 0.560 (−15.1 dB) on Tracker Pre; neither was changed.

## Interpretation

The devices have broadly similar monitoring latency with these driver settings.
At 48 kHz/128 frames the measured path is about 18.5–18.8 ms; at 512 frames it is
about 34.5–36.1 ms. At 96 kHz/256 frames it is about 18.0–18.9 ms. Use the
per-device tables and failed-check counts rather than interpreting these rounded
comparisons as recommendations for a stable buffer setting.

## Method

Both cables stay on the device: right output to input 2, left output to input 1.
An experimental variant of hal-loopback generates a chirp only on the right
output. In the same duplex IO callback it copies input 2 to the left output.
Input 1 is recorded only, never forwarded, so the software path cannot feed back.

The recorded right channel is the reference and the recorded left channel is
the signal after software monitoring. Both are captured against one clock.
Cross-correlating each with the chirp and subtracting right delay from left delay
measures the additional forwarding path. Interpreting this as analog input 2 to
analog output 1 latency assumes the two ADC channels have equal delay: the
measurement ADC delay on input 1 then cancels the reference ADC delay on input 2.
This assumption was not independently calibrated.

This measures a minimal Core Audio IOProc with no effects or application buffering.
A DAW's monitoring path may differ or add plugin/buffering delay. It does not
measure the interface's hardware direct-monitor path.

## Why the old estimate was optimistic

The stock hal-loopback latency command measures converter/device loopback delay
and then prints an estimate using **one IO buffer + both safety offsets**.
However, the observed output/input timestamp separation was **two IO buffers +
both safety offsets**. The forwarding measurement includes that larger separation.
For example, at 48 kHz/512 frames the first forwarding run measured 34.855 ms:
1456 frames of callback separation plus about 217 frames of device/converter delay.
The one-buffer estimate for that run would be approximately 24.19 ms.

Stock loopback runs also found device delay varying between about 4.45 and 5.52 ms
at 48 kHz, with many runs failing the declared-latency tolerance. Do not replace
the driver's latency constants from this experiment alone. The old estimate and
production tool remain unchanged in this measurement-only work.

## Evidence and reproduction

[Raw logs, source and hashes](../../captures/latency/2026-11-16/) include ordinary
loopback runs and `monitor-0404-*` / `monitor-tracker-pre-*` forwarding runs, plus a machine-readable
`forwarding-summary.json`. The experimental source is a frozen copy of the test
with only one-way routing and forwarding-result reporting changed. It is an
experiment, not a new supported command; use its `latency` command only, without
`-i`. Ordinary same-channel latency/equality checks were removed because the two
channels intentionally have different paths. Existing stream-health, chirp
correlation and within-run repeatability checks remain enabled.

From the repository root, build without installing anything:

```sh
clang -std=c17 -Wall -Wextra -O2 -I tools/hal-loopback \
  captures/latency/2026-11-16/monitor-test.c \
  tools/hal-loopback/analysis.c tools/hal-loopback/selftest.c \
  -framework CoreAudio -framework CoreFoundation -o /tmp/emu-monitor-test
EMU_DEVICE=3F04 /tmp/emu-monitor-test -a -18 -r 48000 -b 128 -n 8 latency
# With the cables on Tracker Pre:
EMU_DEVICE=3F0A /tmp/emu-monitor-test -a -18 -r 48000 -b 128 -n 8 latency
```

Use the wiring above, hardware monitoring off, and no other audio clients.
The command sets the rate and buffer and does not restore them automatically.
Chirp amplitude is -18 dBFS in the command; stock chirp generation doubles its
amplitude internally. Set input gains to avoid clipping. Latency testing resets
session diagnostic counters. A nonzero exit status is retained as a failed run,
even when a numerical latency is printed.
